Get started

Getting started

Biorouter is a desktop research environment that connects local, institution-hosted, and commercial AI models in one interface. It runs on your machine, stores its data on disk, and talks only to the model you choose. Getting set up takes a few minutes: download, connect a provider, and start a session. This guide covers biorouter 1.88.3 on macOS, Windows, and Linux.

1

Download and install

Grab the build for your platform from the Download page or from GitHub Releases.

  • macOS: open the .dmg and drag Biorouter to /Applications (a .zip is also published for the auto-updater).
  • Windows: unzip the .zip and run Biorouter.exe.
  • Linux desktop: sudo dpkg -i biorouter_*.deb or sudo rpm -i BioRouter-*.rpm.
  • Linux headless (servers, HPC nodes, containers): install the CLI-only package biorouter-cli_*.deb / biorouter-cli-*.rpm. It ships just the biorouter CLI and the biorouterd daemon, with no GUI.
Node isn't required to run the app. Biorouter's backend is a native Rust binary. You only need Node 24+ if you install an extension whose MCP server launches through npx.
2

Put the CLI on your PATH (optional)

The biorouter command-line app ships inside every desktop download and shares the same config, sessions, knowledge, and skills as the GUI — switch between them freely.

  • From the app: click Install Biorouter CLI when the app offers it on launch. One click symlinks the bundled binary into the first writable, on-PATH location.
  • From a terminal: run biorouter setup-path. If the target directory isn't on your PATH, it prints the exact line to add.

Then run biorouter doctor to check prerequisites (git, uv, python, node, AWS CLI), confirm the CLI is on your PATH, and check for updates.

3

Connect your first provider

Biorouter guides you through this on first launch. Pick whichever fits your trust boundary:

  • UCSF researchers: choose Versa API Azure (UCSF ChatGPT) or Versa API Bedrock (UCSF-hosted Anthropic). Your data stays inside UCSF's tenant. See Providers & models for the exact fields.
  • Everyone else: paste an API key for Anthropic, OpenAI, Google Gemini, or another commercial provider.
  • Zero setup, fully local: pick Llama Server to use Biorouter's bundled llama.cpp runtime. No key, no install, and nothing leaves your machine.
4

Start your first session

Send a message in the desktop chat, or open a terminal session:

biorouter session        # interactive terminal chat
biorouter run -t "Summarize ./notes.md in 5 bullets"   # one-shot, headless

Every conversation is saved to a local SQLite database under ~/.config/biorouter/sessions/, so you can resume it later from either the app or the CLI.

Where your data lives

Biorouter keeps everything under your user config directory — plain files you can inspect, back up, and version:

PathHolds
~/.config/biorouter/config.yamlProviders, models, extensions, and settings
~/.config/biorouter/sessions/Conversation history (SQLite)
~/.config/biorouter/knowledge/Knowledge bases (markdown + git)
~/.config/biorouter/skills/ · workflows/Installed skills and workflows

Secrets never touch config.yaml

API keys and credentials are written to your operating system's credential store (macOS Keychain, Windows Credential Manager, Linux Secret Service), not to any config file. See Configuration & security.

Working from the command line

Everything the app does is available in the terminal too. Run biorouter (or biorouter session) for the interactive full-screen UI, or a subcommand for scripted work. When output is piped or redirected, the CLI automatically switches to a plain-text path so it scripts cleanly.

Run biorouter <command> --help for the full flags of any command.

Providers & models

Biorouter connects local, institutional, and commercial models through one interface, so you can match each task to the right trust boundary and switch whenever you want. Providers are grouped into three tiers; Local ranks first everywhere because nothing leaves your machine.

The in-app model picker is the source of truth

Model lineups change constantly. Rather than reprint a list that goes stale, Biorouter reads each provider's live catalog and shows it in Settings → Models (and via biorouter models list <provider>). Trust the picker for the exact models available to you today.

Local — zero setup

The strongest privacy guarantee is keeping data on your own machine, and Biorouter makes that the default-easy path.

Llama Server (bundled, recommended)

The desktop app ships a pinned llama.cpp llama-server binary and manages it as a sidecar process, so you can run capable local models without installing Ollama or anything else. Pick Llama Server in onboarding or Settings → Models, choose a model, and Biorouter downloads the GGUF weights from Hugging Face on first use and starts the server for you. Reasoning is on by default with a model-native context window. No API key; nothing leaves the device after the one-time download.

Ollama

If you already run Ollama, Biorouter detects it automatically — pull any model and select it. Everything stays on your machine.

Linux note: the bundled local models need glibc ≥ 2.35 plus libssl3/libgomp1 (Debian 12+/Ubuntu 22.04+). The app itself still runs on older systems; only local inference requires this floor.

UCSF institutional

UCSF-managed endpoints keep prompts and completions inside UCSF's own cloud tenant, which is what makes them appropriate for institution-approved, sensitive work.

Versa API Azure (UCSF ChatGPT)

UCSF's institutional AI platform, accessed via Azure OpenAI. Get your API key by signing in with UCSF MyAccess at ai.ucsf.edu/…/ucsf-versa, then open Settings → Models → Azure OpenAI → Configure.

FieldValue
Endpointhttps://unified-api.ucsf.edu/general
API Version2025-01-01-preview
API KeyYour UCSF Versa API key
ModelThe current default GPT deployment is pre-selected; pick another from the picker.

Versa API Bedrock (UCSF-hosted Anthropic)

UCSF provides Anthropic Claude models via Amazon Bedrock, routed through UCSF's gateway so your data does not leave UCSF infrastructure. Open Settings → Models → Amazon Bedrock → Configure and enter just two values — Biorouter fills in the region and proxy endpoint and persists the credentials for you.

FieldValue
Profile NameAny label, e.g. UCSF Bedrock
AWS Access Key IDProvided by UCSF (not personal AWS SSO credentials)
AWS Secret Access KeyProvided by UCSF
ModelPick a permitted Claude model from the picker.

Both UCSF providers expose an Enter a model not listed… option. Use it when UCSF announces a deployment newer than Biorouter's curated list; otherwise prefer the pre-verified entries to avoid deployment-not-found or access-denied errors.

Commercial cloud

Bring your own key (or cloud credentials) and Biorouter surfaces that provider's full model list. Configure any of these from Settings → Models:

Anthropic OpenAI Google Gemini GCP Vertex AI Azure OpenAI Amazon Bedrock Databricks Snowflake Cortex OpenRouter LiteLLM Venice AI GitHub Copilot X.AI · Grok z.ai · GLM Xiaomi MiMo Tetrate SageMaker TGI

Any OpenAI-compatible endpoint can be added as a custom provider — point Biorouter at the base URL and key and it works like any built-in one.

Switching models

  • Globally: Settings → Models → select a provider card → Configure or Launch.
  • Per session: change the model mid-thread from the chat's model menu without losing history.
  • Per workflow: pin a provider, model, and temperature in a workflow's settings block so a shared task reproduces exactly.

Multimodal input: vision-capable models (across Anthropic, OpenAI, Gemini, Bedrock, and others) accept image attachments in chat. Biorouter enables image upload per session based on the active model's advertised capabilities.

Three things extend what the agent can do: extensions give it tools over the Model Context Protocol (MCP), skills teach it repeatable methods, and the BAAM marketplace one-click-installs both. Add a capability once and it works in every session.

These ship with Biorouter — no install needed. Enable or disable any of them from Settings → Extensions.

Adding any MCP server

Any MCP-compatible server can be added as an extension. In the desktop app, open Settings → Extensions → Add custom extension and pick the transport:

  • stdio — a local command Biorouter launches (e.g. a uvx or npx server).
  • Streamable HTTP — a remote MCP server reached over a URL.

Or declare it in ~/.config/biorouter/config.yaml:

extensions:
  spokeagent:
    name: SPOKEAgent
    cmd: uvx
    args: [--from, "git+https://github.com/BaranziniLab/SPOKEAgent", spokeagent]
    type: stdio
    enabled: true
  remote-agent:
    name: My Remote Agent
    url: https://my-agent.example.com/mcp
    type: streamable_http
    enabled: true

Most UCSF agents launch through uvx (install uv); a few use npx (install Node 24+).

Skills

A skill is a folder containing a SKILL.md file — YAML frontmatter (name, description) plus freeform instructions that teach the agent to do one thing the same way every time. Biorouter loads every skill under ~/.config/biorouter/skills/ and activates the relevant ones automatically.

Around 85 skills are published through BAAM, grouped by category:

  • Core — scientific research, R and Python scripting, ggplot visualization, HPC helpers, and writing skills.
  • Developer — code review, code simplification, commit helpers, skill authoring, and frontend design.
  • Biomedical — single-cell, variant calling, differential expression, pathway analysis, spatial transcriptomics, proteomics, clinical biostatistics, and more.

Install a skill by dragging a .zip onto Skills → Add Skill in the app, or with biorouter skill install ./bundle.zip. Skill folders are plain text — share them across a lab to standardize analysis style without sharing any data.

Knowledge & Auto Visualiser

Two features turn raw material into something the agent can use and you can read: a knowledge base that digests your sources into a connected, git-backed wiki, and the Auto Visualiser that renders structured data as self-contained interactive figures.

Knowledge base

A knowledge base is a personal, LLM-maintained store of structured information: a folder of markdown pages backed by a full git history. You never hand-edit it — Biorouter reads your sources, writes cross-linked pages, grades credibility, and commits every change. Because it is plain markdown under git, everything stays local, readable, diffable, and reversible.

Local by design. Bases live entirely under ~/.config/biorouter/knowledge/<kb-id>/. Git is statically built in, so no system git is required. The only network calls are credibility lookups (Crossref / OpenAlex) and your configured model.

How ingest works

Add a source — a file, a URL, or pasted text — and Biorouter runs it through a deterministic pipeline:

1

Convert

The source is converted to markdown with format-specific handling for HTML, PDF, DOCX, and CSV (plus spreadsheets, PPTX, and plain text).

2

Digest

A bounded sub-agent reads the converted text and writes or updates interlinked wiki pages — sources, entities, and concepts — connecting them with Obsidian-style [[links]] that form the knowledge graph.

3

Commit

Every operation commits atomically — it lands completely or not at all — so you can browse the history and roll back any change.

Searching and using it

  • Query: ask a question and Biorouter searches the base with BM25 + graph traversal and writes a cited answer, optionally filing it back as a new page.
  • Lint: a hygiene scan that finds orphan pages, contradictions, and stale sources, with an autofix option.
  • Credibility: each source is graded on a deterministic ladder (DOI/PMID lookup → Crossref → OpenAlex → host patterns), and retractions are flagged as a badge on the graph.
  • Grounding: the chat agent reads from visible bases on every turn. Biorouter uses a hide-from-the-agent model — every base is available unless you hide it, and one base is the active default.

In the app and the CLI

Open the Knowledge route in the sidebar to create a base (⌘K / Ctrl-K palette), drop in files or paste text, watch streamed digestion progress, explore the force-directed graph, and open the change-log to preview or restore any past commit. Export or import a whole base as a single .brkb archive. From the terminal:

biorouter knowledge create my-kb --name "My KB"
biorouter knowledge ingest --kb my-kb --url https://example.com/paper
biorouter knowledge ingest --kb my-kb --file ./report.pdf
biorouter knowledge query "what does the cohort show?" --kb my-kb --save
biorouter knowledge lint  --kb my-kb --fix

Apps & Agent Drafter

Agent Drafter builds Biorouter apps: a TypeScript front-end wired to its own agent — one that drives the interface, not just chats inside it. The agent renders panels, charts, and graphs, highlights regions, switches themes, and asks the user questions, all through typed ui_* tools. Use it when a workflow needs a richer surface than chat: cohort reviewers, calculators, knowledge-map explorers, data dashboards, or lab-specific tools.

The Apps SDK v2

Generated apps import a small client runtime and talk to a per-app agent over a WebSocket. The SDK gives you:

PieceWhat it provides
br.* client runtimePrompt, stream, cancel, subscribe to events, read context usage, and live-switch the model (br.model) — plus br.kb for knowledge access
Component catalogAgent-driven UI primitives — panels, charts, graphs, tables, notifications — applied to the DOM by the SDK
Shared reactive stateA single state document the app and agent both read and write, so the UI stays in sync across turns and reconnects
Capability-gated securityUI control is on by default (its blast radius is the app's own page); files, data, and compute are deny-by-default and granted explicitly per app
Theme packsThe app inherits Biorouter's look, or the agent can restyle it within allowed bounds
Multi-agent worker profilesAn app can define named worker profiles the primary agent consults for sub-tasks

The agent drives the app

Authors mark render targets with a region attribute, e.g. <section data-br-region="results">. The agent discovers them with ui_describe and writes to them with tools like ui_panel, ui_render, ui_chart, ui_graph, ui_highlight, ui_theme, and ui_ask — each pushing a frame down the app's socket that the runtime applies to the page. Because ui_ask blocks the tool call until the browser replies, the agent can branch on the user's answer inside a single turn.

Building an app

Agent Drafter exposes tools for the whole lifecycle:

ToolPurpose
create_appScaffold a project with starter HTML, TypeScript, and a manifest
configure_appSet persona, model, extensions, skills, knowledge base, capabilities, and guardrails
update_appEdit the HTML, TypeScript, CSS, or assets
build_appBundle the source with esbuild and refresh the vendored SDK
lint_appCheck SDK wiring, self-contained assets, controls, and launch readiness
launch_app · preview_appOpen the app locally or preview it inline
export_appWrite a standalone, directly runnable project

Exported apps are directly runnable

export_app writes a self-contained project that runs without any build step: a manifest.json, the bundled front-end, launch scripts (run.sh / run.command), and a small server that proxies to a local Biorouter daemon. No Node is required — the launcher locates biorouterd, starts it, and opens the app. Exported apps carry no API keys; they inherit the credentials of whoever runs them.

Workflows & automation

A workflow is a portable file (YAML or JSON) that packages everything an agent needs to run a task the same way every time — the instructions, a prompt, typed parameters, the extensions and skills to enable, and the model to run on. Workflows are the foundation of federated collaboration in Biorouter: instructions travel between institutions, data does not.

Anatomy of a workflow

A minimal workflow needs a version, title, description, and at least one of instructions or prompt. Everything else is optional.

version: 1.0.0
title: Literature review
description: Summarize recent papers on a research topic.

instructions: |
  You are a scientific literature reviewer. Search for relevant
  publications and write a structured summary focused on clinical
  relevance and methodology.

prompt: |
  Summarize the past {{ years }} years of work on {{ topic }}.

# typed parameters surfaced as a form ({{ name }} in the prompt)
parameters:
  - key: topic
    input_type: string      # string | number | boolean | date | file | select
    requirement: required
  - key: years
    input_type: number
    default: 3

# pin a provider/model for reproducibility
settings:
  biorouter_provider: versa_bedrock
  temperature: 0.2

# pre-enable extensions and prefer specific skills
extensions:
  - { type: builtin, name: developer }
skills: [scientific-research]

# activity pills shown while it loads
activities: [Fetch papers, Summarize findings, Cite sources]

# structured output + retry on transient failures
response: { type: object }
retry:    { max_attempts: 3 }

Workflows support Jinja-style templating and inheritance, so a specialized workflow can extend a shared base and override just what it needs. A response schema requests structured output; retry handles transient provider errors.

Discovery

Biorouter finds workflows from several places, so a lab can keep shared ones in a repository while you keep personal ones local:

SourceLocation
Global library~/.config/biorouter/workflows/
Project-local./.biorouter/workflows/
Custom pathBIOROUTER_WORKFLOW_PATH
RemoteA GitHub repository of workflow files

Running, creating, and sharing

  • Run: Sidebar → Workflows → pick one → fill parameters → Run (in the current chat or a new tab), or biorouter run --workflow review.
  • Create from a session: after a useful exploratory chat, Workflows → Create from session extracts the instructions, the extensions you actually used, and the model into a fresh, editable YAML file.
  • Share: workflow files are plain text with no embedded data — commit them, publish on GitHub, email them, or share a deeplink. Recipients open them with Import workflow.

The Scheduler

Biorouter's built-in cron Scheduler runs any workflow unattended — even when the app is closed. Create a schedule from the GUI (Sidebar → Scheduler) or the CLI, and each run is recorded as an ordinary session linked back to the schedule.

biorouter schedule add --schedule-id review-weekly --cron "0 8 * * 1" --workflow-source ./review.yaml
biorouter schedule run-now --schedule-id review-weekly
biorouter schedule sessions --schedule-id review-weekly --limit 20

From the Scheduler you can run a job on demand, pause or resume it, edit its cron, stop a running job, and inspect its recent sessions.

Configuration & security

Biorouter is built for sensitive research data. This section covers how settings resolve, how the agent's actions are gated, where secrets live, and how to keep regulated data inside an approved boundary.

Configuration and precedence

Non-secret settings live in ~/.config/biorouter/config.yaml; most can also be set with environment variables. When the same setting is defined in more than one place, the higher-priority source wins:

PrioritySource
1 (highest)Managed policy — an administrator-provisioned config that overrides everything below it
2Environment variables (e.g. BIOROUTER_*)
3config.yaml
4 (lowest)Built-in defaults

Permission modes

Permission modes govern how much the agent can do on its own before it acts — specifically for tools that touch your machine, such as shell, text_editor, and computer_control. Set the mode in Settings, per chat, or from the classic CLI (/mode …).

ModeBehavior
Completely AutonomousThe agent runs tools without asking. Best for trusted, sandboxed tasks.
Manual ApprovalEvery gated tool call pauses for your explicit approval.
Smart ApprovalRoutine, low-risk actions run automatically; anything sensitive asks first.
Chat OnlyThe agent responds in text and never invokes machine-touching tools.

Where secrets are stored

API keys and credentials are never written to config.yaml. By default Biorouter stores them in your operating system's credential store:

PlatformSecret store
macOSKeychain
WindowsCredential Manager
LinuxSecret Service (e.g. GNOME Keyring)

Setting BIOROUTER_DISABLE_KEYRING=true falls back to a plaintext secrets.yaml — use only on trusted, isolated machines. Headless Linux without a Secret Service falls back to this automatically.

Working with PHI and patient data

Never use personal commercial API keys with patient data, PHI, or other regulated research data. Route sensitive work only to a local model (Llama Server or Ollama, which never leaves your device) or a UCSF-managed provider (Versa Azure or Versa Bedrock, which keep data inside UCSF's tenant). Always verify with your institution's compliance office before processing regulated data.
  • De-identify first. Remove names, dates of birth, MRNs, and other identifiers before any AI processing.
  • Minimize exposure. Provide only what the task needs.
  • Protect the device. Session logs can contain your inputs; never share a session that contains sensitive data.

Enterprise and headless deployment

  • Managed policy: administrators can ship a policy config that pins providers, enforces permission modes, and locks settings across a fleet — it sits above user config and environment variables.
  • Headless server mode: on a server, HPC node, or container, run the biorouterd daemon from the CLI-only Linux package and drive it from a browser UI — no desktop GUI needed.

Themes

Three theme families ship with Biorouter, selectable in Settings. Each works in light and dark mode:

ThemeFeel
Parchment · defaultWarm, cream-toned — the app's base look (and the palette of this site)
Alma MaterUCSF navy with teal accents
Roche LimitA cool, JupyterLab-inspired palette

Troubleshooting

If something misbehaves, run biorouter doctor to check prerequisites and updates, and inspect the logs (path shown by biorouter info). Settings → App → Reset can clear specific categories — applications, knowledge, skills, extensions, schedules, workflows, or conversation history — with a preview and confirmation before anything is removed.

Report an issue

Attach a diagnostics bundle and file it on the GitHub issue tracker, or ask in the community Slack. Bug reports and feature requests are welcome.

Architecture

Biorouter is a modular, plugin-based system: a native Rust backend and an Electron + React front-end, connected over a local REST and WebSocket API. It is organized as three layers.

Three layers

  • Interface — the desktop GUI (Electron + React 19 + TypeScript) or the terminal CLI. Accepts input and renders responses.
  • Agent core — a Rust reasoning loop managing LLM interaction, tool dispatch, context-window management, and session state.
  • Extensions — pluggable MCP servers that provide tools: file system, databases, web, code execution, and custom agents.

The Rust workspace

The backend is a single Cargo workspace (Rust 1.92) under crates/. The version lives in exactly one place, so the three shipping binaries can never disagree at build time.

CrateBinaryRole
biorouter—Core agent library: the reasoning loop, 40+ provider implementations, the MCP extension manager, session state (SQLite), workflow execution, context management, the scheduler, and the Knowledge service.
biorouter-clibiorouterThe interactive terminal app and headless runner.
biorouter-serverbiorouterdThe local Axum REST + WebSocket server the desktop app talks to; the TypeScript API client is generated from its OpenAPI spec.
biorouter-mcp—The built-in MCP servers (Developer, Computer Controller, Memory, Auto Visualiser, Tutorial, Knowledge, Agent Drafter) plus the Knowledge engine.
biorouter-acp—An Agent Communication Protocol implementation for multi-agent orchestration.

Built on tokio (async), axum (HTTP), rmcp (MCP), sqlx/SQLite (sessions), minijinja (workflow templates), tokio-cron-scheduler, and a vendored libgit2 (knowledge history — no system git needed).

How the pieces talk

CLI  → calls the biorouter crate APIs directly
GUI  → Electron main spawns biorouterd → React renderer
       communicates over HTTP / WebSocket (typed client from OpenAPI)

Every extension speaks MCP, a standard protocol for LLM tool invocation. Any MCP-compatible server — a local process or a remote HTTP endpoint — can be added as a Biorouter extension, which is what makes the ecosystem open and extensible.
