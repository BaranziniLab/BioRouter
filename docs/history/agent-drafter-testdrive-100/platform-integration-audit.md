# Platform integration audit

> **What this is.** An audit separating four different things the 100-app test drive kept conflating:
> what an app spec *requested*, what Agent Drafter *wrote into the manifest*, what the isolated
> runtime actually *had installed*, and what a browser turn demonstrably *exercised*.
> **Status:** Historical record — the audit is closed and its headline finding was fixed. It carries
> no date of its own; it samples specs 001–016 of the July 2026 run. The invented knowledge-base and
> skill identifiers it found were remediated in Wave 1: `list_platform_catalog` and write-boundary
> rejection now exist in `crates/biorouter-mcp/src/agent_drafter/catalog.rs`. The corrective protocol
> it prescribed "from spec 021 onward" was applied to a run that ended at spec 025.
> **Audience:** maintainers of Agent Drafter and the Apps SDK.

The governing rule of this audit is that a configured name is not a working integration. An app that
writes `knowledge_base: "clinical-guidelines"` into its manifest has demonstrated nothing if no such
knowledge base is installed — and, as the audit found, the platform would then arm a tool that could
only fail. This finding is carried as finding 11 in the
[audit findings register](audit-findings-register.md).

## How to reproduce the queries

Every catalog query below was run through the same CLI and environment the apps themselves used: the
isolated BioRouter environment rooted at `.br-testdrive/runtime` via `BIOROUTER_PATH_ROOT`, whose app
store is `.br-testdrive/runtime/config/biorouter/agent_drafter` (see
[pre-run-baseline-gates.md](pre-run-baseline-gates.md)). Inside that environment the queries are
`biorouter knowledge list`, `biorouter extension list`, and `biorouter skill list`. Running them
against a normal shell reads the *user's global* catalogs and will not reproduce the empty results
below. The sandbox itself was ephemeral and is not checked in.

The machine-readable inventory is generated by
`scripts/agent-drafter-testdrive/audit_platform_integrations.py` and stored as
[`data/platform-integrations.json`](data/platform-integrations.json).

## What the isolated runtime actually provides

| Capability | Available in `.br-testdrive/runtime` |
|---|---|
| Built-in extensions | `developer`, `computercontroller`, `autovisualiser`, `memory`, `tutorial`, `agent_drafter`, `knowledge` |
| External extensions | none |
| Connector-style external integrations | none configured |
| Installed runtime skills | none |
| Installed knowledge bases | none |

> **Note on connectors.** Apps SDK v2 has no separate `connectors` manifest field. Connector-like MCP
> integrations would be represented as external extensions, and none are installed in this isolated
> run. Codex-side connectors are not BioRouter app-runtime capabilities and are not credited here.

> **Note on the user's global skills.** The user's global BioRouter profile exposes several general
> skills, but the test contract keeps every persistent app and runtime file inside the worktree.
> Those global skills are therefore not silently imported or credited to isolated apps.

## What specs 001–016 configured

This table samples the first 16 apps, which were the apps that had been authored and re-audited when
this audit was written. Authoring later continued to spec 025; those apps are not counted here.

| Manifest feature | Apps configuring it | Real status |
|---|---:|---|
| Any extension | 16 / 16 | Built-in names are real |
| `knowledge` extension | 15 / 16 | Real extension, but no installed KB payload |
| `autovisualiser` extension | 15 / 16 | Real built-in; UI/scientific rendering is available |
| One or more skill ids | 7 / 16 | All unavailable in the isolated skill catalog |
| Concrete `knowledge_base` id | 13 / 16 | All unavailable in the isolated KB catalog |
| Non-empty knowledge grant ids | 8 / 16 | All unavailable grants |
| Model routes | 6 / 16 | Structurally configured on the locked UCSF model; runtime route selection still needs per-app evidence |

Runtime history shows attempted skill or knowledge use in specs 001, 003, 004, 008, 010, and 011.
Because the isolated catalogs are empty, these attempts do not prove a working skill or a grounded KB
integration; several visibly failed or returned insufficient data. No external connector ran.

## Corrective protocol prescribed from spec 021 onward

This section records the protocol the audit prescribed at the time. The run reached spec 025 before
stopping, so it applied to five apps.

The Agent Drafter order and the static reviewer were changed to receive the exact isolated catalog,
and to:

- configure only the seven real built-in extensions;
- never invent external extension, connector, skill, or KB identifiers;
- when a requested skill, KB, or connector is unavailable, leave ids unset (empty knowledge grants)
  and document the unmet requirement honestly;
- enable `knowledge` or `autovisualiser` only as real built-ins;
- require non-empty UCSF-locked `orchestration.routes` when the spec asks for model routes;
- require non-empty `orchestration.workflows` when the spec asks for workflows;
- require `autovisualiser` when the spec asks for scientific figures; and
- distinguish configured, available, and runtime-exercised status in every result instead of awarding
  credit for a manifest string.

Specs 001–020 were re-audited under these stricter rules. Invalid skill and KB claims were to be
removed only through Agent Drafter refinement, never by hand. Exports remained deferred to the
runbook's final cross-app export phase and were not to be marked exercised before that phase ran.

> **Note.** The remediation later moved this protocol out of prompting and into the product. Wave 1
> added a real catalog and rejected unknown ids at the write boundary; re-linting the corpus with the
> fixed platform caught 19 of 30 apps on invented ids. See
> [remediation-results.md](remediation-results.md).

## Per-app evidence fields

The audit defined this schema for each subsequent per-app result, so that a manifest string could
never again be mistaken for a working capability. It is a template, and the run ended before every
app carried all five fields.

| Field | Meaning |
|---|---|
| Requested | What the idea's `Platform integration` line asks for |
| Configured | Manifest extensions, skills, KB grants, routes, workflows |
| Available | Exact configured entries present in the isolated catalog |
| Exercised | Browser or session evidence that a real tool, route, or workflow ran |
| Missing/blocked | Requested integration unavailable, or configured falsely |
