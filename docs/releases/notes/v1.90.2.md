# Biorouter v1.90.2

A patch release. Three bugs reported from inside the app by its own bug reporter,
each investigated to its root cause rather than to its symptom.

## The composer said "working" over a finished chat

Pressing Stop on a turn whose cancel request failed — a dropped connection, a
response that did not confirm settlement — latched a flag that gated the return
to idle. Nothing ever cleared it. From that moment on **every later turn in that
chat** ended with the composer's working edge still sweeping and the Stop button
still in place of Send, over a conversation that had plainly finished.

The latch exists for a real reason: a terminal frame can beat the cancel response
by a few microtasks, and the composer must stay gated until the server confirms
the turn slot was released. That race is over the moment the response resolves,
whichever way it resolved, so the flag is now cleared in a `finally` — no later
early return can strand it again. As defence in depth the gate is also scoped to
the turn generation it was armed for, so a terminal frame for a *different* turn
returns to idle whatever the flag says.

Confirmed as a before/after in the running app, with the cancel forced to fail
and the turn then allowed to complete normally: before, the composer stayed
pinned; after, it returns to idle and Send comes back.

## Branch could throw away the whole conversation

Branching a long chat could produce a branch holding only the first exchange.

The anchor identifying "branch from this message" was resolved with a
first-match search, and when the id resolved to nothing it fell through to a
whole-second timestamp comparison. Either arm could cut anywhere, and the
narrowest reading always won. That pairing is not hypothetical: the desktop's
live view is structurally short of the store — one streamed reply becomes two or
three rows and only the first keeps the id the client was shown — so an id the
window holds can name an earlier row, or no row at all.

Anchor resolution now follows one rule: **a branch that keeps too much is
recoverable, one that discards the conversation is not.**

- An id resolving to a message older than the timestamp beside it is stale; the
  branch widens to the whole conversation instead of cutting there.
- An unresolvable id keeps everything rather than degrading to the timestamp.
- A duplicated id resolves to the last match, never the first.
- The timestamp anchor cuts a prefix instead of filtering each message
  independently — `created` is not monotonic in a real chat, and the old filter
  orphaned tool responses from their requests.
- The recorded branch point is the anchor actually honoured, not one that was
  refused.

A genuine per-message Branch still cuts exactly where it was clicked.

## Skills would not say what could be removed

`searchSkills` returned `{name, description, bundle}` and nothing more, so no row
said whether Biorouter shipped the skill, whether an installed extension supplied
it, or what name a removal would take. Because removal validates the whole batch
before touching disk, one shipped name rejected all of them — and the rejection
named only the first offender, so the only route to a valid batch was to re-send
it once per offender. A real 14-name batch died on `about-biorouter` with nothing
removed.

Each result now carries `builtin`, `source`, `extension`, `removable` and
`removalTarget` — the exact name to pass, which for a bundle member is the bundle
rather than the skill. Every field is derived from the catalog's own root list
and from the same predicate the removal preflight asks; none of it is a second
list of names to keep in step. This is also what finally makes an
extension-supplied skill legible as such, instead of looking like a package the
user installed and may delete.

A rejected batch now names every offending target at once, grouped by reason,
alongside the ones that would have been removed. One retry is enough.

## Notes for maintainers

The three fixes are independent and touch disjoint files: the composer fix is
renderer-only, Branch is in the session store, and skills spans the catalog and
the skills extension.

Worth knowing for anyone verifying a renderer fix in the dev GUI: a
`.vite/build/main.js` from a production forge build loads the renderer from
`file://`, ignoring any running vite dev server, so a "verified" run can be
executing a hours-old bundle. Check the window's URL before trusting the result.
