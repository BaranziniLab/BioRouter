# Biorouter v1.90.1

A patch release. Four capabilities the agent could not reach before, and the
security fixes an adversarial review of them turned up before they shipped.

## The agent can now manage what you already could

Three asset types were manageable by the model and one was not. Measured in a
live session with 91 advertised tools: knowledge bases had 22 tools, extensions
8, skills 7, and workflows **zero** — even though workflows already had eleven
HTTP routes behind them. The sharpest symptom was that the model could *schedule*
a workflow, which takes a path, while having no way to *list* one.

- **`platform__manage_workflow`** — list, read, generate from the current chat,
  save, delete, validate, export, import and schedule. Mutating actions park on
  an approval showing what will change; on a `biorouter serve` daemon, which can
  never ask a person, they are absent from the action list rather than offered
  and then refused.
- **`platform__report_bug`** — reads this chat's own record of failed tool calls,
  grades them, and drafts a report. It **asks rather than guesses**: when the
  evidence is not conclusive it says what it can see ("this chat has 0 failed
  tool calls") and puts the question back to you. Filing parks on an approval
  showing the exact text, because a GitHub issue is public and permanent.
- **`kb_delete_base`** — an agent can clean up a knowledge base it created. The
  delete removes the directory and its git history, the registry row, and every
  piece of selection state that pointed at it.
- **A Run button on shell code blocks.** A `bash` or `sh` block in the chat now
  carries a Run control beside Copy. It opens the in-app terminal if none is
  open and runs the command there, so the click is still you running it — you
  just stop copy-pasting. It appears only in the live transcript, never in a
  shared or read-only one.

**One core, not four.** The rule this work was built to satisfy is that
"create workflow from this chat" runs the same logic as the tool. It did not
before: the HTTP route enriched a generated workflow with the session's
extensions and knowledge bases while the CLI did not, the CLI wrote YAML through
a different writer, and `biorouter run --workflow` silently dropped `skills:` and
`knowledge_bases:` because no CLI path called the runtime. All four surfaces now
call one core in `workflow/service.rs`.

**And the desktop entry point is alive again.** "Create workflow from this chat"
opened on a window event that had three listeners and no dispatcher anywhere in
the app — a modal with 21 passing tests that could not be opened. It is wired to
a real control, and the settings, author and version it generates now survive
being saved, which they previously did not.

## Security, found before it shipped

An adversarial review of the four features raised 18 findings; 10 survived
independent verification. The ones that mattered:

- **A generated workflow carried live connector credentials.** The captured
  extension set came straight from the running config, where a `Bearer` token
  typed into Settings is stored verbatim and never keyring-migrated. `generate`
  returns the rendered YAML as *tool content*, so the whole document — token
  included — was appended to the conversation and sent to the model provider on
  the next request, including to a coding-agent child on a consumer plan with no
  BAA. `save` then wrote the same document to the library people mail around.
  The capture now applies the same projection the session export already used.
  A share link is covered too.
- **A chat privatised mid-turn could be filed to a public tracker.** The bug
  reporter's disclosure gate read the privacy tier as it was when the turn began.
  The classification is a ratchet a tool call can raise mid-turn — reading a
  private knowledge base is enough — so a chat that was private *now* could be
  published on a stale reading, with the approval card showing the stale value.
  The tier is read at the moment of the decision, and a read that fails refuses.
- **`Authorization: Basic` and `curl -u user:pass` survived the scrubber.**
- **The approval card truncated the body it was asking you to approve.**

## Also fixed

- A knowledge-base delete waited out a 1800-second lock on a base another chat
  had open; it now gives up in 45 and says so.
- An unreadable page tree reported "0 pages removed" rather than admitting it
  did not know.
- The workflow id cache stamped its freshness before scanning, so a miss never
  rescanned and a renamed file was served to delete and schedule.
- `/workflow` in the CLI destroyed a generated workflow when validation failed,
  and said nothing about why.
- An import card named only the title while the payload could declare arbitrary
  extension commands.
- A multi-line block sent to the terminal is bracketed by what the shell actually
  asked for, so a heredoc no longer executes line by line.
- An approval card raised from inside a platform tool reached the user. It was
  published and then delivered nowhere, so the turn stopped with no dialog and
  the parked call sat out its full 15-minute time-to-live — which a user sees as
  a chat that silently stops.
- The workflow generator's prompt and the system prompt every workflow run
  receives were both five months stale; three dead UI files were removed.

## Notes for maintainers

The recursive-delete gate's Windows story was mis-diagnosed twice during this
work and the record is worth keeping: 25 `sensitive_ops` failures on
`windows-latest` were POSIX fixtures meeting a PowerShell default dialect, not
an inert gate. They are gated to non-Windows with the reasoning written into the
test module. Windows still has no coverage of that criterion — its path is
`Remove-Item -Recurse -Force` and needs its own fixtures.
