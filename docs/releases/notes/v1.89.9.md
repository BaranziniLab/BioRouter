# Biorouter v1.89.9 release notes

**Release date:** August 27, 2026

**Repository:** [github.com/BaranziniLab/biorouter](https://github.com/BaranziniLab/biorouter)

v1.89.9 is a follow-up to v1.89.8. It makes a coding-agent child say what tools it
really has before it reaches for one it does not, and it fixes a test-suite deadlock
that had been failing continuous integration on macOS and Windows for months.

⚠ **It also carries the source v1.89.8's own tag does not.** The v1.89.8 artifacts
were built from a commit eight ahead of the tag `v1.89.8` points at, because the
GitHub tag is stamped when a release draft is created rather than when it is
published, and that release was rebuilt after its draft. The shipped binaries were
correct; `git checkout v1.89.8` does not match them. This release's tag is created
after its final build.

## Codex and Claude Code are told which tools are real

A coding-agent child is a whole agent, and Biorouter switches its own tools off:
everything it does should go through Biorouter's tool bridge, behind the inspectors,
permission mode, `.biorouterignore`, vault and privacy gates. The vendor CLI keeps
*advertising* the disabled tools anyway, so a model asked to delegate would call
Codex's own `spawn_agent` and get back `no thread with id` — an error naming nothing
the user did and nothing they could change, which made a perfectly healthy bridge
look broken.

- The child's instructions now name the tools it actually has, read from the live
  grant rather than a hard-coded list, and say plainly that its own sub-agent tools
  are unavailable here. A child with no bridge is told nothing, so it is never
  promised tools it does not have.
- If a model reaches for one regardless, the vendor's internal error is rewritten to
  explain whose machinery it is and what to do instead.

Re-enabling the vendor's multi-agent feature would silence the message too, and would
hand the child exactly the unmediated surface the bridge exists to deny. It stays off.

## Continuous integration

`test (macos-latest)` and `test (windows-latest)` had been running to their timeout
and being cancelled, reporting only that a couple of tests had "been running for over
60 seconds" — and one of those two was merely queued behind the other. Roughly three
thousand passing results were discarded with each cancelled job.

The cause was not a deadlock in the application. Test session ids are minted as
`PREFIX_N`, where `N` counts existing sessions **in that database** — and every test
builds its own temporary database, empty. So every test's first session had the same
id as every other test's first session, while the registry of running sub-agents is
shared across the whole test process and keyed by exactly that id. A test that left a
handle behind handed it to whichever later test minted the same id, and that test
waited on it forever.

In tests the id prefix now comes from the store's own directory instead of the date.
Nothing about the shipped application changes.

Two further test fixes travelled with it: a sandbox test asserted a path would be
passed through literally, which is only true when that path does not exist on the
machine running it; and the sub-agent tests now bound their runs, so a future
deadlock fails by name in two minutes rather than consuming a job.
