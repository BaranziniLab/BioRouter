# v1.89.0 verification log

> **What this is.** The running record of how v1.89.0 was verified before release: what was
> tested, how, what broke, what was fixed, and what could not be tested here. Written as the
> work happened, not reconstructed afterwards.
> **Status:** Current — the release is being built and verified; it is **not** published.
> **Audience:** Anyone deciding whether this build is fit to ship, or diagnosing something it missed.

## Ground rules for this pass

- **Model.** Every verification that drives the agent uses **`versa_azure` / `gpt-5.5-2026-04-24`**
  (UCSF Versa GPT). No Anthropic model is used for verification — cost. Any run that reaches a
  different provider is void and must be repeated.
- **Config is sandboxed.** Driving the GUI uses a throwaway `XDG_CONFIG_HOME`. Launching the dev
  GUI has previously wiped `~/.config/biorouter`, and the user's real config holds live provider
  keys and knowledge bases.
- **Never drive the user's running app.** A packaged copy or a dev build only.
- **Real input, not synthetic.** `CDP Input.dispatchMouseEvent` bypasses the macOS window server
  and reports success regardless, so it cannot test anything involving drag regions, window
  moves, or tear-off. Those need `CGEventPost`. CDP is for *reading* state and screenshots.
- **A claim without a reproduction is a hypothesis** and is labelled one here.

## Findings

Numbered `F-nn`. Each records how it was found, because the *method* is the reusable part.

### F-01 — one cosmetic edit hid 2,443 test results (fixed)

`privacy::visibility::tests::the_matrix_has_production_callers` cuts
`workspace_extension.rs` at its `#[cfg(test)] mod tests` to scan only production text. A
workspace change made that module `pub(crate)`, the scan pinned the exact string
`"#[cfg(test)]\nmod tests {"`, stopped matching, and **panicked** — taking the entire
`biorouter` test binary down before any other test ran. Cargo then halted, so no other
workspace binary ran either.

The lane that made the change ran only its own two modules (98 tests) and never saw it.

**Fixed** by stepping over an optional visibility modifier instead of pinning one spelling. The
test's negative control — which proves the cut actually removed the test module — is what
establishes correctness, and it works for any spelling.

**The lesson is not "update both scans".** It is that a guard which *panics* rather than fails
takes its whole binary with it, so an unrelated edit can silently delete an entire suite's
coverage while CI still shows one red line.

### F-02 — `GET /diagnostics/{session_id}` returned a full private transcript, ungated (FIXED)

`crates/biorouter-server/src/routes/status.rs` contains **zero** `session_reach` calls, while
`routes/session.rs` — whose two routes return *the same bytes* — has three. The diagnostics
route reaches `generate_diagnostics` → `export_session` → the full message list, written into
`session.json` inside the returned zip.

`session_reach.rs`'s own header says of the gated sibling: *"an unguarded sibling of a guarded
read is the defect this campaign keeps shipping."* This is another one. The manual test
checklist covers `/export` and `/events` and omits this route too.

Not covered by the DR-17/AR-11 ruling: that ruling accepts the daemon cannot *authenticate* a
local caller, whereas the reach gate keys on *capability*, a different axis.

### F-03 — the session-store capability was guarded at one door of three (FIXED, one seam open)

`SessionStoreInspector` is registered only at `agents/agent.rs`. The directly analogous
`global_memory` capability is guarded at three places — the inspector chain, `POST
/agent/call_tool`, and tool calls made from inside `execute_code` — plus an MCP-side barrier. A
literal store path in script text is caught; a runtime-assembled one is not, which is the exact
walk-past that made the global-memory boundary refusals necessary.

The lane that built the inspector declared this openly in its module header. No lane picked it up.

### F-04 — `rustlock.sh` silently no-ops, so some "verified builds" verified nothing (open)

The lock script runs `"$@"` with no PATH setup, and `cargo` is not on the agent shell's PATH, so
it exits 127 with `cargo: command not found`. Piping to `tail` then hides it. **Any lane that
reported a green build through that harness reported nothing.** Every build claim made via the
lock needs re-running with `PATH="$PWD/bin:$PATH"`.

### F-05 — two gated routes had no test at all (FIXED, and partly refuted)

Of the seven routes on `session_reach.rs`'s gated list, four are pinned by the ordering census
and five by the HTTP bypass tests. `/sessions/{id}/export` and `/sessions/{id}/events` have
neither. **Deleting either gate today fails nothing.**

### F-06 — `SessionListView` "flake" was a real product bug (FIXED)

Two tests failed when their file ran whole and passed when siblings were skipped. Bisection
disproved two hypotheses — a leaked mock implementation surviving `clearAllMocks`, and pollution
from the neighbouring shared-cache tests — and the repo's own `src/test/timeouts.ts` warns this
symptom "was misdiagnosed as [machine contention] more than once."

It was neither. **`SessionItem` was declared inside `SessionListView`'s render body.** React
compares element types by identity, so every parent render produced a *new type*: React unmounted
every row and mounted a replacement, discarding each row's DOM node. `React.memo` cannot help —
memo compares props, and a fresh type never gets that far.

A `MutationObserver` probe showed the row being replaced 8 ms after mount, so the node the test
held was already `isConnected=false` and `fireEvent.click` never reached React's delegated
listener. Running alone, the same replacement landed ~1 ms *after* the query resolved, which is
the entire difference between pass and fail. **Load only moved where the replacement landed; the
defect that made a re-render fatal was the unstable type.** The same cause explained the second
file, proven by an old-vs-new component experiment.

So the "flake" was the messenger: in the shipped app, every re-render of the session list
destroyed and rebuilt every row's DOM.

Fixed by moving `SessionItem` to module scope and making `setSessionRefs` a stable `useCallback`.
The workarounds it had forced into the tests — a settle-before-click, and a retry inside
`waitFor` — were removed, since a retry there would now mask a regression. No assertion was
changed, relaxed, skipped or retried. **20/20** repeated file runs; **5/5** full-suite runs at
2436/2436.

**The lesson:** an intermittent test failure is a hypothesis about the test. Here it was evidence
about the component, and two rounds of test-focused debugging (mine) missed it.

### F-07 — `privacy_toggle` hung on the macOS Keychain (FIXED)

`crates/biorouter/tests/privacy_toggle.rs` never finishes.
`the_master_toggle_governs_every_gate_in_both_directions` runs **> 7 minutes alone with
`--exact`** — so it is neither lock contention between tests nor `--test-threads` related. A
full-workspace run reports 30 of 31 binaries (2633 passed, 0 failed) and then dies at this one.

Ruled out: guard reentrancy. The file's `set_privacy_tiers()` helper warns it is not reentrant
and "deadlocks rather than failing", but both hanging tests correctly `drop()` before
re-acquiring.

**Why it was invisible until now:** cargo stops at the first failing binary, and
`tests/providers.rs` was failing earlier on a live Anthropic call against an exhausted credit
balance — aborting every run *before* this binary. Removing the key made providers skip and
exposed it. **That is the second finding this week where a failure early in the sequence hid
everything behind it**, after F-01.

### F-08 — the test suite makes live, billed provider calls (open, by design)

`crates/biorouter/tests/providers.rs` fires a **real** request to every provider whose key is
present in the environment, and skips the rest. With `ANTHROPIC_API_KEY` set it billed Anthropic
and failed on an exhausted balance. Without it, all thirteen skip and the binary is 15/15 green.

Not a defect — but it means **`cargo test` costs money depending on the shell's environment**,
which is surprising, and it silently aborted every full-suite run for an unrelated reason. Every
run in this pass uses `env -u ANTHROPIC_API_KEY`.

## Independent review: waived for this release, by the operator

The release process asks for an independent `/codex` review. It did not happen,
and this records why and on whose decision.

Codex was unavailable: nineteen review jobs sat at `running` for 101–119 hours
across every phase with no live process. They had not stalled — each had failed
at submission on **"You've hit your usage limit"** (credits available again
2026-08-09 13:01) and been left in the running state, which `status` never
surfaced. A dead reviewer that reports "waiting" scores as a pass, so no
twentieth job was queued. All nineteen were cancelled.

An OpenRouter provider is configured in `~/.codex/config.toml` and could have
carried the review at additional cost. **The operator was offered wait / reroute
/ waive, and chose to waive it for 1.89.0.**

⚠ **What that leaves unreviewed.** This release adds a helper-process
authentication path (`biorouter-authprompt`) whose approval crosses local IPC
and is therefore forgeable by anything running as the user — a deliberate
weakening over the in-process call it replaces, accepted because that call never
fires under the desktop app. `HOWTOAI.md` asks for human review of security
logic. The evidence standing in its place is not equivalent, and is listed here
so it is not mistaken for equivalent:

- Every substantive change mutation-tested: the guard was written, the
  implementation then broken deliberately, and the guard confirmed to fail.
  Including the nonce check (forged nonce, permissive verdict) and the
  bundling guard.
- `release.sh verify` green across all 11 artifacts, including deb/rpm/CLI
  executed in clean Debian and Rocky containers.
- The packaged app opened and inspected: the helper is present, arch-matched,
  and observed launching from the shipped bundle with no environment override.

### F-11 — six server-lib tests broke on a seam neither branch owned (FIXED)

Five `routes::reply::tests` posted to session ids that were never persisted. `POST /reply` joined
the privacy-gated list, so the gate resolved them as unreadable and returned 403 where they
expected 200. Fixture-only repair — each now creates a real session, following the idiom the

catch two evasions the old form could not.

### Defects

#### P-01 — a renderer reload mid-turn loses the transcript for that window's lifetime

Reload the window (not the tab) while a turn is running and the chat shows
**"Connection dropped — The connection dropped before the response finished. Retry to continue where
it left off."** and stays there.

What actually happened underneath is the interesting part. The daemon **finished the turn normally**:
`TOOL_EXEC_END … dur_ms=30133`, then the summary streamed, then
`Session completed … exit_type="normal" … total_tokens=5201`. All four messages persisted —
`sqlite3 sessions.db` shows the toolRequest, the toolResponse and the final assistant text. The cost
chip even moved to $0.06. Only the view is wrong.

It does not self-heal: still "Connection dropped" 24 s after the turn ended, and still there after
navigating to Home and back into the session. A **full app restart** renders the complete transcript.
So: work done, work paid for, work invisible.

The reconnect path leaves a fingerprint at the moment of the reload —
`routes::agent: No background task found, loading extensions for session 20260807_3` — i.e. the
reconnecting renderer was not matched to the in-flight turn, which is precisely what the tab-close
path (P-01's passing sibling) gets right.

Severity: high, but bounded — no data loss, and Cmd-R is not a common gesture in a desktop app.

#### P-02 — a merge drop closes every window involved (ship blocker)

**Reproduced twice, from a clean two-window state the second time.**

1. One window, two tabs. Real-drag tab 2 outside the window → tears off into a second window. Both
   windows healthy, one tab each.
2. Real-drag the torn-off tab onto the *other* window's tab-strip band — a point inside that
   window's strip and outside the source window.
3. **Both windows close.** Not "the tab moved and the source closed" — the target closes too.

After the first run the app was left with only a stray Home window that had been created earlier;
after the second, with **zero windows**. `System Events` reports `count of windows = 0` while the
process is alive, no crash in the app log, and activating the app does **not** re-create a window.
The only recovery observed was quit-and-relaunch.

Sessions are safe — everything is in `sessions.db` and reappears in Recents on relaunch — so this
destroys layout, not data. But merge is one of the two things 1.89.0 advertises, and its failure
mode is "your windows vanish".

The drop point in run 2 was chosen to be unambiguous: (600,100), inside the target's strip band
(x 296–1392, y 70–121) and outside the source window (x ≥ 1120). Only `ipcMain.on('close-window')`
closes a window in `main.ts`, so the likely shape is that the **target** window ends up sending it
too — but that is a hypothesis, not a measurement.

#### P-03 — enabling the Workspace extension does not persist

The extensions menu lists Workspace as the only toggleable entry and ships it **disabled**. Toggling
it on (either the row or *Enable all (1)*) flips the menu to "Disable all (1)" and the tools **do**
become available to the running session — the agent listed all eight. But `config.yaml` still reads
`workspace: enabled: false`, and after an app restart the menu is back to "Enable all (1)".

So BR-71 is off by default and cannot be turned on durably from the UI. The override is
session-scoped; the config write does not happen.

#### P-04 — the extension counter reads 0 while eleven extensions are loaded

The composer chip says `Manage extensions (0 enabled)` on a session where `developer`,
`computercontroller`, `autovisualiser`, `memory`, `knowledge`, `agent_drafter`, `todo`, `chatrecall`,

#### P-05 — the privacy-tiers control never completes (blocks the capability-raise check)

Driven entirely with real OS input, verifying state between every step:

1. Real click on the *Privacy tiers* switch → the typed-confirmation panel opens. The copy is

   extensions, read private chat history… **While it is off, Biorouter stops recording which

3. Real click on *Turn off privacy tiers* → the switch goes to `data-disabled` (`busy === true` in
   `PrivacyPanel`) **and never comes back**. Checked at +2 s, +5 s, +10 s, and +60 s: still busy,
   still `checked`, no error rendered, no `privacy-enforcement-off-strip`.

`BIOROUTER_PRIVACY_TIERS` is never written to `config.yaml`; `privacy-tiers.json` keeps its
first-boot `changed_at`. The daemon log's **last line predates the click by four minutes** and
contains no refusal, no 403 and no tier route hit — so the `upsert(PRIVACY_TIERS_KEY, …)` promise in
`PrivacyPanel.write()` appears never to resolve, and the request may never leave the renderer.

`busy` is set before the await and cleared only in `finally`, so a promise that never settles parks
the whole panel — the switch and the confirm button both go dead until a reload.

**Consequence for the acceptance question.** The precondition is satisfied: the packaged daemon
holds a user-action digest (no `no user-action key on stdin` in any run). But a capability raise was
**neither accepted nor refused** — it never got an answer. So "confirm a capability raise is actually
accepted" is **not** established by this pass, and the reason is a UI hang rather than the daemon
refusal that was feared.

### Harness notes for whoever repeats this

- `page.fill()` on the privacy confirmation input sets the DOM value **without** updating React
  state, so the confirm button stays disabled and it looks like an app bug. `keyboard.type()` on a
  focused input works. Half an hour was lost to this.
- `CGEventPost` needs the app frontmost *at the moment of the click*; any intervening Playwright
  call can steal focus. Re-raise (`System Events … set frontmost`) immediately before every real
  click, and verify the step landed before doing the next one.
- Tear-off needs a drop **outside the window's content rect** — inside is `local` by design.
- The daemon's port and secret are not exposed to the renderer (`appConfig` holds neither), which is
  the AR-11 posture working as intended and means the HTTP API is not a shortcut for driving the
  packaged app. Drive the UI.

**P-02 — a merge no longer closes every window.** Two runs, each from its own clean launch with a

| | run A | run B |
| --- | --- | --- |

### New finding

#### F-12 — the extension menu's tier label is stale across a session switch (minor)

Navigating from a public-tier chat into a private-tier one **in the same window** leaves the
composer's extension dropdown showing `Unavailable in this chat (public model)` under `Cdwagent` and
`Ucsfomopagent`, on a chat the daemon classifies `private` (`20260807_5`, `turn:versa_azure`).
Reloading the renderer on that same session clears the label and both rows return.

So `privacyTier` reaching `BottomMenuExtensionSelection` is not refreshed when the focused session
changes; `extensionPairingRefused` then compares against the previous chat's tier. The error is in
the **safe** direction — a private chat is shown as more restricted than it is, never less — and
`extensionPairingRefused` returns `false` for an undefined tier rather than guessing, so this is an
accuracy defect in the label, not a hole in the barrier. It also depresses the dropdown's own
counter ("Enable all (5)" instead of "(7)") for as long as it lasts.

Not fixed here, per the scope of this pass.

### Harness notes added by this pass

- **The user's installed `/Applications/BioRouter.app` runs under the same process name and the same
  bundle id** (`com.electron.biorouter`). `tell process "Biorouter"` therefore targets whichever
  copy AppleScript finds first — it reported four windows that were not the sandbox's. Scope every
  AX query and every raise by **pid** (`first process whose unix id is …`). The disposable copy also
  claims `biorouter://` on launch, because `main.ts` claims the scheme when `app.isPackaged`; run
  `lsregister -u <copy>` afterwards so a deleted scratch copy cannot linger as the handler.
- **The focus-theft note from the first pass is the single biggest time sink here, and it is
  under-stated.** Every intervening Playwright call can steal focus, and a `CGEventPost` click that
  lands on another window is *silent* — the renderer simply records no event. That reads exactly
  like an overlay covering the control, and half an hour went into hunting a non-existent one.
  Raise by pid immediately before **every** real click, and instrument the page with a capture
  listener (`document.addEventListener(t, …, true)`) so a click that did not land is visible as an
  empty event log rather than as a mysteriously inert button.
- A probe click placed to test reachability can also *navigate the app* — one landed on **Home** in
  the sidebar and every subsequent selector lookup then failed against the wrong view. Re-read
  `location.hash` after any exploratory click.
- Radix `TabsTrigger` (Settings' Models/Chat/Privacy/App) does not switch on a synthetic
  `element.click()`; use a real click, or `data-testid="settings-privacy-tab"` with one.
